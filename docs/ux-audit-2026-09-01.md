# UX audit — 2026-09-01

Scope: the experience of the answers themselves and how they are displayed,
measured against `docs/product-vision.md` and `AGENTS.md`. No code was changed.

## Verdict in one paragraph

The documents say the right things and the pipeline shape is reasonable. The
experience falls short for three structural reasons, none of which is "the
prompt needs more rules": (1) the editor's output schema cannot express an
outbound link, so the model literally cannot do what the vision asks;
(2) the deterministic adapter between researcher and editor decides what the
editor is allowed to see, pre-titles it, truncates it, and orders it, which is
where the "database dump" feel and the hidden rules live; (3) the frontend is a
card grid with the conversation pinned in a sidebar, not a reading experience.
A fourth, softer cause: the editor is told to avoid anything "not grounded in
the brief," which suppresses the very Deadhead knowledge the persona depends on.

## Findings mapped to the intended outcomes

### 1. "Fascinating Deadhead, not an encyclopedia"

- The editor prompt ends with "Avoid inventing commentary that is not grounded
  in the brief" (`deadbot/composer.py:129`). The brief is mostly IDs, dates and
  set positions, so there is nothing for the persona to be fascinating with.
  The instruction is correct; the brief is starved. Lore must be sourced, not
  recalled from training data. Today every lore tool is metadata-only: titles,
  URLs, one-line descriptions and "why open" hints (`get_lore_source_trails`,
  `search_deadnet_editorial`, `search_stored_resources`). The researcher can
  point at lore but cannot read any. The fix is the source-reader the
  architecture already anticipates (`docs/experience-architecture.md`, quote
  card and permitted source-reader): a sandboxed tool that reads approved-host
  pages and returns short attributed excerpts, so the researcher hands off
  sourced lore text and the editor writes from it with attribution.
- Insight-bearing tools never reach the editor as material. Set-neighbor stats
  (`get_song_performance_profile`), equipment history, weather, astronomy,
  selection signals have no candidate projection in `deadbot/composition.py`.
  They reach the editor only if the researcher paraphrases them in prose.
- The researcher prompt (`deadbot/graph.py:17`) is good. It asks for contrast,
  surprise, continuity, listening paths. But the handoff is a single text
  message; whatever the researcher noticed that does not match a block type is
  compressed to a paragraph the editor may or may not keep.

### 2. "Move naturally among songs, performances, shows, venues, musicians..."

- Every navigable item is a `follow_up` string authored by code, not the model:
  "Tell me about the show on 1972-08-27." (`composition.py:325, 458, 506, 604,
  671, 783, 847`). The visitor sees the same sentence template everywhere.
- Venues and people are entities in the graph but have no block or card. A
  venue is only a subtitle on a show card. A musician is only a follow-up
  button. The vision names both as first-class stops.
- The main column refreshes to the latest turn only (`_latest_turn`). That is
  a fine choice, but it means there is no visible trail; the thread on the left
  is plain text with no links, so the visitor cannot step back into a previous
  answer's body.

### 3. "Direct and trustworthy; richer material as an inviting path"

- Candidate titles are hard-coded and database-shaped: "Known performances",
  "First and last performances", "Performances over time", "Set context",
  "Jerry's guitars", "Further reading and listening", "Chord charts and
  arrangements", "Recordings", "Performers". The editor can reuse a candidate
  but cannot retitle it. The eyebrows in `web/src/App.tsx` add more system
  vocabulary: "Canonical performance evidence", "Musician's reference",
  "Sources", "Lineup", "Equipment".
- Coverage disclaimers are baked into candidates as copy (`composition.py:408`
  comparison strip note, `:569` show selection default note, `:797`
  arrangement search note) and rendered under the card. AGENTS.md asks for
  coverage context only where it changes meaning.
- The sources footer shows "Canonical / External source" chips for every
  response. That is provenance paperwork made visible by default.

### 4. "Links to recordings, interviews, community discussion"

- Schema: `EditorialItem` has `follow_up` but no URL (`deadbot/experience.py:344`).
  The chat answer is rendered as plain text (`App.tsx:641`), so a URL the
  editor writes there is inert. The model cannot link out from anything it
  writes itself. The only outbound links come from whole reused candidate
  blocks (`recording_list`, `resource_list`, `media_link`, `arrangement`).
- Data: `data/canonical/show_links.csv` and `performance_links.csv` each hold
  one row. There are effectively no YouTube/Spotify/relisten links to attach.
  `recordings.csv` has ~18k archive.org rows but no per-song entry point, so a
  song question can never offer "hear this version." Official release tracks
  exist for a slice. This is an ingredient gap; no prompt fixes it.
- `_recording_list` truncates to the first 8 rows in CSV order
  (`composition.py:727`), with no quality or source-type signal, so the editor
  chooses among an arbitrary eight. Selection signals (Charlie Miller, critic
  picks) exist in the library but are not attached to the recordings the editor
  sees.

### 5. "Clear priority aligned with the request"

- `get_show` always returns lineup and equipment (`deadbot/data.py:391-467`),
  and the adapter always projects both as candidates ahead of the setlist:
  entity card, performers, equipment, setlist, recordings (`composition.py:1029-1059`).
  The editor sees them in that order with equal weight. A weaker model
  follows the order it is given. Nothing in the brief says "the regular lineup
  is the default; only deviations are interesting."
- The equipment candidate is pre-titled "Jerry's guitars" (`composition.py:682`)
  and styled in its own warm color (`styles.css:94`), so when the editor keeps
  it, it is visually louder than the setlist. The `get_show` docstring also
  nudges toward guitars ("or Jerry Garcia's named guitars, reuse the most
  recent retrieved show ID"), which is a content hint inside a tool contract.
- `_latest_turn` plus the adapter's fixed ordering means the editor is never
  told what the visitor's previous turn already showed, so consecutive show
  questions repeat the same lineup card.

## Deterministic rules found in the model's way

These are the places where code, not the model, makes an editorial decision.
They should be removed or moved into the model's brief.

| Where | Rule | Why it hurts |
| --- | --- | --- |
| `composition.py:349, 727, 1171-1174` | `items[:20]`, `[:8]`, `arrangements[:3]` truncation before the editor sees candidates | Editor selects from a pre-selected set it never saw the rest of |
| `composition.py` block builders | Hard-coded titles and coverage copy | Editor cannot retitle or drop disclaimers |
| `composition.py:243-249` | Drop a song card if it has no `original_artist` | Content decision hidden in the adapter |
| `composition.py:196-202` | Approved research hosts hard-coded | Duplicates the source registry; policy in two places |
| `composition.py` follow_up templates | Code writes every follow-up sentence | Same phrasing everywhere; model cannot pose a better next question |
| `composition.py:965-1060` | Fixed candidate order per payload type | Order acts as an implicit priority the editor inherits |
| `composer.py:67-77, 146` | Any invalid candidate index invalidates the whole plan, which becomes a 503 | One slip by the model turns into a dead end for the visitor; drop the bad index instead |
| `composer.py:39` | `body_blocks` max 8, layout chunked by 8 into "primary / supporting" | "Keep exploring" label appears mechanically after block 8 |
| `App.tsx:10-25` | Mode and region labels are code-authored copy | System vocabulary as headline eyebrows |
| `tools.py:404, 471` | Stop-word lists inside search tools | Brittle keyword rules; low harm, but a smell |
| `tests/test_experience.py:236` | Test asserts exact prompt wording | Prompts cannot be iterated without editing tests |

## Design and layout

- The co-pilot layout stays: the left pane is the conversation, the main panel
  is the experience. The problems are inside each pane, not the split.
- Left pane: the composer is pinned to the pane bottom (`styles.css:36`), far
  from a short answer. Requested behavior: the input sits directly under the
  latest message and docks to the pane bottom only when the thread overflows.
  That is the composer as the last child inside the scrolling thread with
  `position: sticky; bottom: 0`.
- Header overlap: the pane is a fixed-height flex column where the masthead is
  `flex-shrink: 0`, the thread has `min-height: 11rem`, and the composer has
  default shrink. On short viewports the composer collapses upward. Fix is
  `min-height: 0` on the thread and `flex-shrink: 0` on the composer.
- Chat bubbles should render restricted markdown so the chat answer can carry
  links and entity references, and so a previous answer stays useful.
- Every block is a bordered card in a 12-column grid, most spanning 6, so any
  two blocks form a box grid (`styles.css:55-56`). Boxes should be reserved for
  objects the visitor acts on (a player, a setlist, a recording list). Narrative,
  facts, credits, and follow-ups should be typography.
- Chat text is `white-space: pre-line` plain text. No markdown, no links, no
  inline entity references.
- Several eyebrows duplicate the card title ("Setlist" over "Setlist").

## Architecture: one loop or two

Reasons the split exists today
- The researcher runs a text tool loop; the editor needs strict structured
  output. Most providers cannot do both in one turn cleanly.
- It lets a cheap model do retrieval and a better one do taste.
- It gives the presentation schema a single, testable boundary.

Costs of the split as built
- The handoff is lossy. Tool JSON is projected to blocks by code; the
  researcher's insight is compressed to one paragraph; some tools have no
  projection at all.
- The editor never saw the question being researched. It cannot ask for one
  more lookup or know why a candidate exists.
- Two prompts and two personas to keep aligned. Two round-trips of latency.
- The adapter between them is where every hidden rule in this audit lives.

Recommendation: merge first. Make the editor's plan the agent's final tool
call (`finish_response(plan)`), validated by the same Pydantic schema. One
persona, one prompt, one context, the model knows what it looked up and why.
The production model is `gpt-5.6-luna`, which carries a 20-tool loop plus a
large structured plan without difficulty, so the weak-model argument for the
split does not apply.

What survives the merge: the block schema and renderer (`experience.py`,
`App.tsx`), every tool, the plan validation in `apply_composition_plan`, and
the candidate builders in `composition.py`. The builders change role: instead
of gating what the editor sees, each tool result carries its renderable
candidates as attachments the finish tool can reference by ID. What is
retired: the second model call in `composer.py` and the researcher-to-editor
prose handoff. Repairing that handoff before merging would be discarded work,
so it is not on the list.

## Recommended order of work

1. Merge the loops with a `finish_response` tool. Fold the two prompts into one
   persona. Include the guidance that the visitor's question sets priority and
   that the regular lineup and gear are background unless the question or the
   show makes them notable.
2. In the same schema pass, let the model link and speak: add a validated
   `link` (url, label) to editorial items, render chat and editorial text as
   restricted markdown where URLs must appear in retrieved material, let the
   model author follow-up prompt text and block titles, and drop invalid
   references instead of failing the plan.
3. Build the approved-host source reader so the researcher hands off sourced
   lore excerpts with attribution, not links alone. Start with the hosts
   already in the registry (dead.net, deadessays, deadheadhigh).
4. Fix the panes: composer in flow under the latest message with sticky-bottom
   docking, header overlap, markdown in chat bubbles. In the main panel,
   reserve cards for players, setlists and recording lists; render narrative,
   facts and credits as typography.
5. Fill the listening ingredient gap: per-song archive.org track links or
   relisten links, more official release track mappings, and attach selection
   signals to recordings so the editor can recommend a source. Two more link
   sources belong here once credentials exist: Spotify track URLs for mapped
   official-release tracks (Spotify Web API, client-credentials flow, keyed by
   the album URLs MusicBrainz supplies) and YouTube performance videos (YouTube
   Data API, searched by song and show date, restricted to the official
   Grateful Dead channel plus a reviewed uploader list). Both need an API key
   or app registration; neither should be scraped. The finish-plan resolver
   must also accept `official_release_tracks.spotify_track_url` and
   `performance_links` URLs as grounded media links.
6. Remove the remaining adapter rules in the table above that the merge does
   not already retire, and re-run the evaluation set.
