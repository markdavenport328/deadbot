## The one-paragraph state

Deadbot is a Grateful Dead knowledge and listening companion: a FastAPI
backend, a LangGraph agent with read-only tools over a reviewed PostgreSQL
library (imported from CSVs in `data/canonical/`), and a React client. As of
PR #9 the agent is a single loop: one model with one persona researches with
the tools and ends its turn by calling `finish_response`, whose arguments are
the whole answer (chat text, title, lead, mode, and a body that mixes
model-written blocks with library components referenced by ID). The old second
model step that projected tool output into cards is gone. The library now has
listening links for nearly every show and every mapped song performance, and
293 official live releases. Production runs at https://deadbot-ten.vercel.app
and answered a live question correctly after the merge. What has not been done:
the new data has not been imported into the production database, real answers
have not been evaluated systematically, and the "learn" side (sourced lore) is
still links with one-line descriptions.

## What the product is trying to be

From `docs/product-vision.md` and the owner's own words: a fascinating,
well-informed Deadhead, research companion, musicologist and DJ. Direct answers
first. Then an inviting path into listening (full shows and specific versions),
reading (interviews, essays, community commentary), and connected entities
(songs, performances, shows, venues, musicians, releases). Not an encyclopedia,
not a database dump, not a generic chatbot.

Two decisions the owner made explicitly, do not reopen them:

- Lore must be sourced. The model does not fill gaps from training data. The
  fix for thin lore is richer sourced context (a source reader), not looser
  grounding.
- The two-pane "co-pilot" layout stays: conversation on the left, the
  experience in the main panel. Improve the panes, do not collapse them.

## First principles that govern every change

`AGENTS.md` is binding. In short:

- Prompts and context are the first avenue of improvement. Prompts hold goals
  and guidance, never rules or checklists. "Equip the chef with ingredients and
  preferences, do not hand him a recipe book."
- Deterministic code is transport and structural integrity only: parse the
  plan, resolve references to retrieved records, render supported blocks. It
  never vetoes an editorial choice, never chooses content by keyword, never
  substitutes a database dump, never forces provenance copy into the page.
- When an answer is weak, improve the model's context, tools, persona, or
  palette. Do not encode the example as a rule. Previous agents did exactly
  that and the audit spent most of its effort rooting those rules out.
- Do not pin prompt wording in tests. Tests assert behavior.
- Do not reintroduce a second model step or a handoff between models.

## How the system works now

Request path: browser question → `deadbot/api.py` (`/api/experience`) →
`deadbot/graph.py` agent loop → tools in `deadbot/tools.py` → the model calls
`finish_response` → `deadbot/finish.py` builds the `ExperienceResponse` →
`web/src/App.tsx` renders it.

| File | Role |
| --- | --- |
| `deadbot/graph.py` | `SYSTEM_PROMPT` (the persona; goals and guidance), `agent_tools()` (read-only tools plus the finish tool), routing (`route_after_model`, `route_after_tools`), `run_config()` (recursion budget `max_tool_rounds * 2 + 4`). |
| `deadbot/finish.py` | `FinishPlan` and the reference models (the model-facing schema), `build_finish_tool()`, `grounded_context()` (ids and URLs the tools returned this turn), `resolve_body()` (references → validated blocks), `build_experience_response()` (plan → response, with logged fallbacks). |
| `deadbot/composition.py` | Block builders only (`_show_setlist`, `_recording_list`, `_performance_spine`, `_song_overview`, …) plus three message helpers. The research host allowlist lives in `_research_resource`. |
| `deadbot/experience.py` | The browser schema (Pydantic, `extra="forbid"`). Changing it requires `PYTHONPATH=. .venv/bin/python scripts/export_openapi.py` then `npm run gen:types --prefix web`; CI fails on drift. |
| `deadbot/tools.py` | Twenty read-only tools: entity search, song/show/performance context, guest search, stored resources, Dead.net metadata search and read, Deadcast metadata, lore source trails, arrangements, equipment history, show selections and signals, media links, weather, astronomy, astrology. |
| `deadbot/data.py`, `deadbot/postgres.py`, `deadbot/storage.py` | `CanonicalStore` (CSV, used by tests) and the PostgreSQL store (production). `storage.py` refuses anything but Postgres at runtime. |
| `deadbot/api.py` | FastAPI app. Built lazily on first access of `deadbot.api:app`, so importing the module needs no database. Replays the browser's transcript into an isolated per-request thread. |
| `web/src/App.tsx`, `web/src/styles.css` | Renderer. Inline markdown links (`renderInline`), editorial item links, ↗ for external links and → for ask-Deadbot follow-ups. |

Behaviors worth knowing, all of them logged so you can measure them:

- If `finish_response` arguments fail validation, the error goes back to the
  model and the loop continues, bounded by the recursion budget.
- If the model ends a turn without calling `finish_response`, the visitor gets
  the last assistant text (or a placeholder) with a gap-state body, and a
  WARNING is logged. Count these; if the rate is material, bind
  `tool_choice="required"` in `OpenAIProvider` rather than adding a retry rule.
- If the chat answer is blank, the lead or a placeholder is shown and the body
  still renders. WARNING logged.
- Exhausting the recursion budget is not graceful: LangGraph raises and the
  API returns HTTP 503.
- Grounding is turn-scoped and id-level: a component can be referenced by any
  canonical ID that appeared in this turn's tool output (search results count)
  and the server fetches it from the store. Links are kept only when their URL
  appeared in this turn's tool output; otherwise the link is unwrapped to its
  label text. Research resources use projected ids
  `research:<source>:<identifier>` and resolve from the turn's payloads; the
  host allowlist in `composition.py` still decides which URLs reach the browser.

2. **Run real questions and read the answers.** Nothing in the merge was

5. **Fix the panes.** Left pane: the composer should sit directly under the

## Decisions parked for the owner or a later pass

- The "Canonical" chip in the sources footer effectively disappeared with the
  projection loop (only contextual sources are emitted now). The audit argued
  it was paperwork; confirm or restore.
- Recording list labels are the source lineage string (for example
  "SBD>16 Track Master Reels>…"), which reads badly. Build a display label from
  source type, taper or transferer, and SHNID instead.
- When the model names specific recording ids and none are grounded, the
  component is dropped rather than replaced by the default list. Deliberate:
  drop, do not substitute.
- `EditorialItem` requires all of `marker/title/value/detail/follow_up`, and
  `EditorialBlock` requires both `paragraphs` and `items`, because the browser
  contract doubles as the tool schema. Defaults would cut finish-validation
  failures for weaker models but change `web/openapi.json`.
- Held data: two Veneta encore track rows (source titles carry an `E1:`
  prefix), 33 releases without a resolvable date, 2,998 unmapped release
  tracks (mostly multi-show compilations without per-track dates), 144
  Relisten dates with no canonical show, early and late shows on one date.
  Each has a review JSONL and a status doc under `docs/collection-status-*.md`.
  Rhythm Devils is now an alias of Drums (decided 2026-09-01).

## Working with the owner

Plain language, short, decisions with a recommendation and the reason. No
process narration, no file-by-file inventories, no jargon that assumes the
reader has watched the work. Explain what a thing is before asking for a
decision about it (they did not know what the CLI or Rhythm Devils were until
told). They notice UX details and care about the felt experience more than the
plumbing. When they push back, they are usually right about the product; adjust
and say what changed.
